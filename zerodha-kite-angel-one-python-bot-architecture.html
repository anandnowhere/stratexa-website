Complete Architecture for Connecting Zerodha Kite & Angel One to Cloud Python Bots

October 15, 2026 Stratexa Engineering Desk 7 min read Broker & API Guide

Over the past five years, the democratization of broker APIs by Zerodha (Kite Connect), Angel One (SmartAPI), and Finvasia (Shoonya) has allowed retail traders in India to deploy institutional-grade automated trading systems without paying tens of lakhs for institutional leased lines.

However, connecting a trading bot requires more than just calling place_order(). A production-ready algorithmic trading architecture must be resilient to network disconnects, enforce rate limits, handle daily 2FA token generation, and execute stop-losses reliably on cloud servers.

1. The 4-Layer Architecture Model

A battle-tested Python trading engine is segmented into four distinct layers:

  • Layer 1: Authentication & Token Management — Automated daily login using TOTP (Time-based One-Time Password) libraries (such as pyotp) to refresh session tokens at 08:45 AM before market pre-open.
  • Layer 2: Tick Data Ingestion via WebSockets — Streaming binary ticks for index futures and option strikes without polling REST endpoints (which trigger broker rate-limit bans).
  • Layer 3: The Signal & Calculation Core — In-memory OHLC candlestick resamplers that evaluate indicators (CPR, Supertrend, EMA) only on closed candles to avoid repainting errors.
  • Layer 4: Order Execution & Reconciliation Engine — Manages margin checks, order throttling (e.g. Zerodha's 10 orders/second cap), and immediate post-order status confirmation via order webhooks.

2. Dealing with Rate Limits and 429 Errors

A common mistake among retail bot builders is hammering the broker's REST API with queries in a tight while True loop. Indian brokers strictly enforce limits:

  • Zerodha Kite: 3 requests per second for quote APIs, 10 requests per second for order endpoints.
  • Angel One SmartAPI: 10 requests per second across endpoints.

Exceeding these limits returns an immediate HTTP 429 (Too Many Requests), which can cause your trading bot to drop an emergency exit order during a sharp market crash. Production systems hold all active state locally and query the broker only when firing transitions.

3. Why Dedicated Cloud Hosting on AWS Matters

Running trading bots on a home laptop over residential Wi-Fi exposes capital to ISP outages, router restarts, power cuts, and operating system sleep modes. Deploying on a lightweight Ubuntu EC2 instance on AWS in the Mumbai region (ap-south-1) reduces broker API ping to under 15 milliseconds and guarantees 99.99% uptime.
